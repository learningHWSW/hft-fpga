TWO CHANGES, EACH AIMED AT A PATH THAT WAS MEASURED RATHER THAN GUESSED.

1. otable_mem never set CASCADE_HEIGHT, so the tool chose, and its choice deepens
   with the table: 2^13 is 2 URAM deep per way, 2^14 is 4. The failing builds'
   worst path ran message FIFO -> order table URAM write with URAM288=3 in its
   logic levels and 70-75 % of the delay in route. Capped at 2 -- the depth of
   the geometry that closes 4 of 4 -- which is a no-op at 2^13.

2. fast_bbo's quantity update was two 32-bit carry chains in series when a delta
   both removed from and added to the best level. Selecting the operands first
   lets the tool fuse a - b + c into one chain. No pipeline stage, so no cost in
   tick-to-trade latency.

WHERE IT LANDS. Every directive now produces a build between 216.5 and 219.8 MHz.
The two that "miss" do so by 0.001 ns on one endpoint each -- the smallest
non-zero violation the tool can report -- against a 4.618 ns yardstick that is
21 MHz above the 195.3 MHz a 100 Gb/s wire demands. The binding path moved at
every step (msg_fifo->URAM, then delta_fifo->fast_bbo qty, now the ladder's
r_add_diff and delta_fifo again), which is what a design sitting on its
constraint looks like rather than a single structural defect.

WHAT IS NOT CLAIMED. This is not "closes on all four directives". Two builds miss
by a picosecond, and a 1 ps margin is not a margin -- it says the constraint is
the arbitrary thing here, not that the design is fragile in the way it was when
three builds missed by tens of picoseconds across 143 endpoints.
